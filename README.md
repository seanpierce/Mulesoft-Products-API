# MuleSoft Products API

## Overview

This project is a local MuleSoft API built with **Anypoint Studio**, **RAML**, **Mule XML flows**, **Java**, **Maven**, and an **H2 local database**.

The API exposes product-related endpoints, such as:

```http
GET /api/products
```

The main purpose of this project is to learn how MuleSoft applications are structured and how an API request moves through the application.

This project demonstrates:

- How a RAML API specification becomes APIkit-generated Mule flows
- How a request enters the main Mule XML file
- How APIkit routes requests to endpoint-specific flows
- How one Mule flow can call another sub-flow
- How Mule XML can invoke Java code
- How Java can connect to a database and return data
- How Maven manages dependencies such as H2 and the Mule Java Module
- How Anypoint Studio organizes and runs a Mule application locally

---

## High-Level Architecture

At a high level, a request follows this path:

```text
Client / Browser / Postman / curl
        |
        v
http://localhost:8081/api/products
        |
        v
products-api.xml
Main HTTP Listener + APIkit Router
        |
        v
get:\products:products-api-config
APIkit-generated flow for GET /products
        |
        v
flow-ref name="get-products"
        |
        v
flows/get-products.xml
Custom Mule sub-flow
        |
        v
Java Module invokes ProductService.getActiveProducts(...)
        |
        v
ProductService.java
Java code queries H2 database
        |
        v
List<Product>
        |
        v
Mule returns JSON response
```

In simple terms:

1. The request enters Mule through `products-api.xml`.
2. APIkit decides which endpoint flow should handle the request.
3. The endpoint flow delegates work to `flows/get-products.xml`.
4. The sub-flow calls Java.
5. Java queries the database.
6. Mule returns the result as JSON.

## Important Files

### `products-api.xml`

This is the main Mule XML file generated by APIkit.

It contains:

- The HTTP listener
- The APIkit router
- APIkit-generated endpoint flows
- Error handling
- Global configuration references

This is where incoming HTTP requests first enter the Mule application.

---

### `flows/get-products.xml`

This file contains custom implementation logic for the `GET /products` endpoint.

Instead of putting all logic directly in `products-api.xml`, the main endpoint flow calls a separate sub-flow.

This keeps the generated APIkit file cleaner.

---

### `ProductService.java`

This is the Java service class that contains the lower-level application logic.

For example, it connects to the database and returns only active products.

---

### `Product.java`

This is a simple Java model class representing a product.

It usually contains fields like:

```text
id
name
sku
price
active
```

Mule/DataWeave can serialize this object into JSON because it exposes getter methods.

---

### `pom.xml`

This is the Maven configuration file.

It defines:

- Project name and version
- Mule runtime version
- Maven plugins
- Java compiler version
- Mule dependencies
- Java dependencies

- Mule Java Module dependency

## What Is MuleSoft?

MuleSoft is an integration platform.

A Mule application is usually made of **flows**. A flow receives a message, performs actions, and returns or passes along a result.

A flow can:

- Receive HTTP requests
- Call APIs
- Query databases
- Transform data
- Call Java code
- Route messages
- Handle errors
- Return responses

In this project, MuleSoft acts as the API layer. It listens for HTTP requests, routes them to the correct endpoint logic, and returns JSON responses.

---

## What Is Anypoint Studio?

Anypoint Studio is MuleSoft’s IDE. It is based on Eclipse.

You can use it in two ways:

1. Visual design mode
2. XML/code mode

This project mostly uses XML/code mode.

In Anypoint Studio, Mule flows can be shown visually as boxes connected together, but underneath, they are stored as XML.

For developers, it is often useful to work directly with the XML because it is explicit and easy to version-control.

## What Is RAML?

RAML stands for **RESTful API Modeling Language**.

It describes what the API should look like.

For example, the RAML file defines:

- The API title
- Base URI
- Endpoints such as `/products`
- HTTP methods such as `GET`, `POST`, `PUT`, `DELETE`
- Request bodies
- Response bodies
- Data models
- Security schemes

Anypoint Studio uses the RAML file to generate APIkit flows.

For example, this RAML endpoint:

```raml
/products:
  get:
    responses:
      200:
        body:
          application/json:
            type: Product[]
```

results in a generated Mule flow like:

```xml
<flow name="get:\products:products-api-config">
    ...
</flow>
```

---

## What Is APIkit?

APIkit is the MuleSoft module that connects your RAML API definition to Mule flows.

APIkit reads the RAML file and creates routes for each endpoint.

For example:

```http
GET /api/products
```

is routed to:

```xml
<flow name="get:\products:products-api-config">
```

This generated flow is where you implement the behavior for that endpoint.

In this project, the APIkit-generated flow does not contain the full business logic. Instead, it delegates to a custom sub-flow.

## Request Flow in Detail

### Step 1: Request Enters Mule

A client calls:

```http
GET http://localhost:8081/api/products
```

This request enters the application through the HTTP listener in `products-api.xml`.

Example:

```xml
<flow name="products-api-main">
    <http:listener config-ref="products-api-httpListenerConfig" path="/api/*">
        <http:response statusCode="#[vars.httpStatus default 200]">
            <http:headers>#[vars.outboundHeaders default {}]</http:headers>
        </http:response>
        <http:error-response statusCode="#[vars.httpStatus default 500]">
            <http:body>#[payload]</http:body>
            <http:headers>#[vars.outboundHeaders default {}]</http:headers>
        </http:error-response>
    </http:listener>

    <apikit:router config-ref="products-api-config" />
</flow>
```

The important part is:

```xml
<http:listener config-ref="products-api-httpListenerConfig" path="/api/*">
```

This tells Mule:

```text
Listen for requests under /api.
```

So this URL:

```http
http://localhost:8081/api/products
```

matches the listener.

---

### Step 2: APIkit Routes the Request

After the HTTP listener receives the request, it passes control to APIkit:

```xml
<apikit:router config-ref="products-api-config" />
```

APIkit checks the RAML file and determines which generated flow should handle the request.

For:

```http
GET /products
```

APIkit routes to:

```xml
<flow name="get:\products:products-api-config">
```

---

### Step 3: The Generated Endpoint Flow Calls a Sub-Flow

Instead of putting all code directly in the generated APIkit flow, this project keeps it thin:

```xml
<flow name="get:\products:products-api-config">
    <flow-ref name="get-products"/>
</flow>
```

This means:

```text
When someone calls GET /products, call the flow or sub-flow named get-products.
```

Important: `flow-ref` does not reference the file name or folder path.

This is incorrect:

```xml
<flow-ref name="flows/get-products"/>
```

This is correct:

```xml
<flow-ref name="get-products"/>
```

Mule looks for a flow or sub-flow with this name:

```xml
<sub-flow name="get-products">
```

The file location does not matter as much as the flow name, as long as the XML file is inside `src/main/mule`.

---

### Step 4: The Sub-Flow Invokes Java

The sub-flow lives in:

```text
src/main/mule/flows/get-products.xml
```

Example:

```xml
<sub-flow name="get-products">
    <java:invoke-static
        doc:name="Get active products"
        class="products.ProductService"
        method="getActiveProducts(java.lang.String, java.lang.String, java.lang.String)"
        target="products">
        <java:args><![CDATA[#[{
            jdbcUrl: p('db.jdbcUrl'),
            user: p('db.user'),
            password: p('db.password')
        }]]]></java:args>
    </java:invoke-static>

    <ee:transform doc:name="Return products">
        <ee:message>
            <ee:set-payload><![CDATA[%dw 2.0
output application/json
---
vars.products
]]></ee:set-payload>
        </ee:message>
    </ee:transform>
</sub-flow>
```

This does two things:

1. Calls a Java static method.
2. Takes the result from Java and sets it as the HTTP response payload.

The Java method is:

```java
products.ProductService.getActiveProducts(...)
```

The returned value is stored in a Mule variable:

```xml
target="products"
```

Then the response payload is set to:

```dataweave
vars.products
```

---

### Step 5: Java Queries the Database

The Java service connects to H2 using JDBC.

Example:

```java
public static List<Product> getActiveProducts(
    String jdbcUrl,
    String user,
    String password
) throws SQLException {
    List<Product> products = new ArrayList<Product>();

    String sql =
        "SELECT " +
        "Id, " +
        "Name, " +
        "Sku, " +
        "Price, " +
        "Active " +
        "FROM Products " +
        "WHERE Active = TRUE " +
        "ORDER BY Id";

    Connection connection = null;
    PreparedStatement statement = null;
    ResultSet resultSet = null;

    try {
        connection = DriverManager.getConnection(jdbcUrl, user, password);
        statement = connection.prepareStatement(sql);
        resultSet = statement.executeQuery();

        while (resultSet.next()) {
            Product product = new Product(
                resultSet.getLong("Id"),
                resultSet.getString("Name"),
                resultSet.getString("Sku"),
                resultSet.getBigDecimal("Price"),
                resultSet.getBoolean("Active")
            );

            products.add(product);
        }

        return products;
    } finally {
        if (resultSet != null) {
            resultSet.close();
        }

        if (statement != null) {
            statement.close();
        }

        if (connection != null) {
            connection.close();
        }
    }
}
```

This method:

1. Opens a database connection.
2. Runs a SQL query.
3. Filters active products using SQL.
4. Maps each database row to a `Product` Java object.
5. Returns a list of products to Mule.

## Configuration

Configuration values should not be hard-coded in Java.

Instead of this:

```java
private static final String JDBC_URL = "jdbc:h2:file:C:/temp/products-db;AUTO_SERVER=TRUE";
private static final String USER = "sa";
private static final String PASSWORD = "";
```

this project uses Mule properties.

---

### `local.properties`

Example:

```properties
db.jdbcUrl=jdbc:h2:file:C:/temp/products-db;AUTO_SERVER=TRUE
db.user=sa
db.password=

http.host=0.0.0.0
http.port=8081
```

---

### Loading the Properties File

In Mule XML:

```xml
<configuration-properties file="config/local.properties"/>
```

This tells Mule to load properties from:

```text
src/main/resources/config/local.properties
```

---

### Reading Properties in Mule XML

Mule can read properties using:

```xml
${property.name}
```

or inside expressions:

```dataweave
p('property.name')
```

In this project, Java method arguments are passed like this:

```xml
<java:args><![CDATA[#[{
    jdbcUrl: p('db.jdbcUrl'),
    user: p('db.user'),
    password: p('db.password')
}]]]></java:args>
```

That means Mule reads the properties and passes them into Java.

## Database

This project uses **H2**, a lightweight Java database.

H2 is useful for local development because:

- It does not require a separate database server
- It does not require firewall changes
- It stores data in local files
- It works well with Java and Maven

The JDBC URL is:

```properties
db.jdbcUrl=jdbc:h2:file:C:/temp/products-db;AUTO_SERVER=TRUE
```

This creates or uses a database at:

```text
C:/temp/products-db
```

You may see files such as:

```text
C:/temp/products-db.mv.db
```

## XML Namespaces

Mule XML files use namespaces to identify which module owns each XML element.

For example:

```xml
xmlns:http="http://www.mulesoft.org/schema/mule/http"
xmlns:apikit="http://www.mulesoft.org/schema/mule/mule-apikit"
xmlns:java="http://www.mulesoft.org/schema/mule/java"
xmlns:ee="http://www.mulesoft.org/schema/mule/ee/core"
xmlns:doc="http://www.mulesoft.org/schema/mule/documentation"
```

If you use an element like:

```xml
<java:invoke-static>
```

then the XML file must include the Java namespace.

If you use:

```xml
doc:name="Get active products"
```

then the XML file must include:

```xml
xmlns:doc="http://www.mulesoft.org/schema/mule/documentation"
```

Otherwise, Mule may show an error like:

```text
The prefix "doc" for attribute "doc:name" is not bound.
```

## Common Errors and Fixes

### `Can't resolve mule-java.xsd`

This means the Java Module dependency is missing.

Fix by adding the Java Module in Anypoint Studio or checking that this exists in `pom.xml`:

```xml
<dependency>
    <groupId>org.mule.module</groupId>
    <artifactId>mule-java-module</artifactId>
    <version>2.0.4</version>
    <classifier>mule-plugin</classifier>
</dependency>
```

---

### `The prefix "doc" is not bound`

This means the XML file uses `doc:name` but does not declare the `doc` namespace.

Add:

```xml
xmlns:doc="http://www.mulesoft.org/schema/mule/documentation"
```

---

### `flow-ref` cannot find flow

Make sure the `flow-ref` name matches the actual `flow` or `sub-flow` name.

Correct:

```xml
<flow-ref name="get-products"/>
```

Must match:

```xml
<sub-flow name="get-products">
```

Incorrect:

```xml
<flow-ref name="flows/get-products"/>
```

`flow-ref` does not use file paths.

---

### Java class not found

Make sure the XML class name matches the Java package.

If the Java file says:

```java
package products;
```

then Mule should use:

```xml
class="products.ProductService"
```

If the Java file says:

```java
package com.mycompany.products;
```

then Mule should use:

```xml
class="com.mycompany.products.ProductService"
```

---

### H2 database appears empty

Make sure Mule and DBeaver are using the same JDBC URL.

For example, both should use:

```text
jdbc:h2:file:C:/temp/products-db;AUTO_SERVER=TRUE
```

If one uses `./products-db` and another uses `C:/temp/products-db`, they may be looking at two different databases.

## Design Notes

This project intentionally keeps Mule and Java responsibilities separate.

### Mule is responsible for:

- Receiving HTTP requests
- Routing requests through APIkit
- Calling sub-flows
- Invoking Java services
- Returning JSON responses
- Loading configuration properties

### Java is responsible for:

- Lower-level database access
- SQL query execution
- Business filtering
- Mapping database rows to Java objects

This is not the only valid design. Mule’s Database Connector can also handle database operations directly in XML.

However, this project uses Java for the service layer to prepare for more complex developer-focused integrations.
